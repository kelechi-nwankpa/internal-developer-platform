# 0037 — Per-session AWS identities enter the cluster at bootstrap, not through Git

- **Status:** Accepted
- **Date:** 2026-11-26
- **Deciders:** project owner
- **Consulted:** —
- **Informed:** future contributors

## Context and problem statement

On EKS some controllers call AWS: the load balancer controller now, and
later cert-manager, external-dns and Crossplane (Phase 9, gaps 4–6).
Each gets an IAM role through IRSA. For that, its ServiceAccount needs
one annotation:

```yaml
eks.amazonaws.com/role-arn: arn:aws:iam::<account id>:role/<role name>
```

Our rule is GitOps-first: if it is not in Git, it does not exist. But
this value does not fit in Git:

- It contains the AWS account id, which the owner does not want
  committed (the account is shared with other projects).
- The role name is generated by CloudFormation, so the value does not
  exist until the stack does.

The same goes for the VPC id, which changes every session.

## Decision drivers

- No account id and no per-session values in Git.
- No commit in the middle of a billed session.
- One pattern for all four controllers, simple enough for a runbook.
- As little as possible outside GitOps, and what is outside must be
  visible and small.

## Options considered

### Option A — Commit the values after each deploy

- Pros: Pure GitOps.
- Cons: Account id in a public repo. A commit, a push and a sync wait
  while the cluster bills. Git history fills with values that were
  valid for three hours.

### Option B — Bootstrap creates the ServiceAccounts (chosen)

Charts are told not to create the ServiceAccount. The session bootstrap
applies a small template from Git, filling in the role ARN from the
CloudFormation output.

- Pros: Git holds everything except one string per controller. Nothing
  to commit during a session. The value is an identifier, not a secret.
- Cons: One object per controller that ArgoCD does not manage. Deleted
  by hand, it stays deleted until the bootstrap is run again.

### Option C — ArgoCD ApplicationSet reading cluster metadata ("GitOps bridge")

The deploy tool writes role ARNs as annotations on ArgoCD's cluster
Secret; ApplicationSets template them into Helm values.

- Pros: The known pattern for many clusters. Charts keep creating
  their own ServiceAccounts.
- Cons: Every EKS app becomes an ApplicationSet with templating, for
  one cluster that lives three hours. Something still has to write the
  cluster Secret at bootstrap, so the out-of-Git step does not go away;
  it only moves.

### Option D — CDK creates the ServiceAccounts (`cluster.addServiceAccount`)

- Pros: One tool makes the role and the ServiceAccount.
- Cons: CDK writes into the cluster through a Lambda. Two tools then
  own cluster objects, and the control plane mutates the data plane
  directly, which principle 1 forbids.

### Option E — Fixed role names, account id in Git

- Pros: The ARN becomes predictable; pure GitOps.
- Cons: Account id in Git. Fixed `idp-` role names also match the
  teardown sweep, so two things would delete one role.

## Decision

**Option B.** Templates live in `platform/eks/bootstrap/`, one per
controller, with a placeholder where the ARN goes. The session bootstrap
(gap 7) replaces the placeholder with the stack output and applies the
file. This is the documented-runbook exception to "no `kubectl apply`
against real clusters", the same kind as installing ArgoCD itself.

For values a controller can find by itself, prefer that over passing
them in: the load balancer controller finds the VPC by its `Project=idp`
tag, so no VPC id is passed at all.

Same idea as the `idp-cluster` EnvironmentConfig that feeds Crossplane
the account id and OIDC provider ([ADR-0034](0034-bucket-access-on-aws-via-irsa.md)).

## Consequences

- **Positive:** No account id, role name or VPC id in Git. No commits
  during a session. One step in the runbook covers every controller.
- **Negative:** A ServiceAccount missing or with a wrong ARN is not
  shown by ArgoCD. It shows as the controller failing AWS calls
  (`AccessDenied` or "no credentials"). The runbook must check the
  annotation after bootstrap.
- **Negative:** The name and namespace are stated three times: the IAM
  trust policy, the Helm values and the template. `make eks-apps-test`
  compares all three.
- **Neutral:** The role ARN is not a secret. Knowing it grants nothing;
  only a token from this cluster for that exact ServiceAccount can
  assume the role.

## When to revisit

- **More than one long-lived cluster.** Option C: the cluster Secret
  becomes the one place per-cluster values live.
- **The account is no longer shared, or the repo is private.** Option E
  becomes reasonable.
